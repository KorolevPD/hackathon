# Структура

- **Единственный источник истины для задач — GitHub Issues** (не TASKS.md). Задачи, имеющие критерии приёмки, входят в процесс; остальные не рассматриваются.
- **Единый шаблон задачи и единый системный промпт генерации Issue** используются и Аналитиком, и UX-дизайнером. Формат одинаковый, различается только инициатор и владелец критериев приёмки.
- **UX-дизайнер не создаёт Issue, затрагивающие бизнес-логику** — только комментирует Issue Аналитика. Чисто интерфейсные/взаимодейственные UX-задачи создаёт сам.
- **Fullstack работает с основным агентом, без суб-агентов для написания кода.** Суб-агент допускается только один — «исследователь кода только для чтения» — и используется Тестировщиком/Тимлидом при необходимости быстро разобрать большой PR.
- **Ответственность за качество — у Тестировщика, за архитектуру — у Тимлида. При конфликте приоритет у Тимлида, но он обязан письменно обосновать причину.**
- Все артефакты (Issues, PR, комментарии) — на русском, названия веток и коммитов — по единому шаблону.


| Роль | Основная ответственность | Ключевые артефакты | Право решения |
|---|---|---|---|
| Аналитик | Бизнес-процессы, границы требований, качество исходного описания | Issue с критериями приёмки (Given-When-Then) | Единственный владелец бизнес-логики |
| UX-дизайнер | Удобство, интуитивность навигации, доступность | UX-Issue (только интерфейс/взаимодействие) или комментарии к Issue Аналитика | Владелец UX-критериев; по бизнес-логике — только предложение |
| Fullstack | Реализация кода в ветке, создание PR | Ветка + PR | Не принимает решений о слиянии |
| Тестировщик | Соответствие PR критериям приёмки, граничные случаи | Approve / Request changes в PR | Владелец качества |
| Тимлид | Архитектура, стек, CI/CD, финальное слияние | Архитектурные Issues, Merge | Владелец архитектуры; при конфликте с Тестировщиком — приоритет, но с письменным обоснованием |

# Пошаговые алгоритмы по ролям

### Аналитик

1. Формулирует задачу устно/письменно, без заботы о формате.
2. Вызывает ИИ с **единым системным промптом генерации Issue** (тот же, что у UX-дизайнера): «На основе неформального описания и структуры проекта сгенерируй черновик Issue: пользовательская история, критерии приёмки в формате Given-When-Then, объём (входит/не входит). Если информации мало — задай 3–5 уточняющих вопросов, не создавай Issue».
3. Отвечает на уточняющие вопросы, **вручную проверяет** критерии приёмки.
4. Создаёт Issue в GitHub с метками `role:*`, `priority:*`, вехой. **TASKS.md не используется.**
5. При необходимости декомпозирует крупную задачу на подзадачи — тем же промптом, без создания отдельных суб-агентов.
6. Отвечает на вопросы Fullstack в комментариях к Issue, обновляет критерии приёмки при изменении решения.

### UX-дизайнер

1. Просматривает dev/main, устно фиксирует UX-проблемы.
2. Классифицирует: **чисто интерфейс/взаимодействие** → создаёт UX-Issue тем же единым промптом (критерии приёмки — про наблюдаемое поведение, например «пользователь достигает переключателя уведомлений за ≤2 шага»). **Затрагивает бизнес-логику** → комментирует Issue Аналитика, решение принимает Аналитик.
3. После реализации проверяет соответствие UX-критериям, при несоответствии запрашивает доработку в PR. **Не блокирует слияние напрямую** — окончательное решение за Тестировщиком и Тимлидом.
4. Использует тот же системный промпт и шаблон, что и Аналитик, чтобы Fullstack получал задачи одинакового качества.

### Fullstack

1. Открывает Issue со статусом `ready-for-dev`, читает критерии приёмки; вопросы — в комментариях к Issue.
2. Создаёт ветку `feat/issue-{number}-short-desc`.
3. **В одном диалоге с основным агентом** (не суб-агентом) передаёт Issue, позволяет прочитать релевантные файлы, генерирует код. Промпт: «Реализуй только критерии приёмки из Issue. Не меняй несвязанные файлы. Верни список изменённых файлов и шаги проверки».
4. Вручную запускает локальные тесты (или поручает ИИ запустить, но результаты проверяет сам).
5. Коммитит, пушит, создаёт PR. Описание PR генерируется ИИ по шаблону: ссылка на Issue, изменения, как проверено, скриншоты (если UI).
6. При запросе доработки возвращается **в тот же диалог** с основным агентом, исправляет и обновляет PR.

### Тестировщик

1. Открывает связанную Issue, читает критерии приёмки.
2. Проверяет diff PR, **вручную** продумывает граничные случаи (пустой ввод, переполнение, повторные клики, сетевые ошибки).
3. При необходимости запускает **единственного суб-агента «исследователь кода только для чтения»** для быстрого разбора большого PR (поиск паттернов, подверженных ошибкам). Решение о принятии — всегда за человеком.
4. Approve → если соответствует; Request changes → с указанием, **какой критерий не выполнен** и воспроизводимых шагов.
5. Не оценивает архитектуру — это Тимлид.

### Тимлид

1. В начале проекта: стек, структура директорий, CI (GitHub Actions: тесты, линтер).
2. Проверяет PR на архитектурную согласованность (соответствие структуре, отсутствие лишних зависимостей).
3. Если Тестировщик одобрил и архитектура в порядке — Merge.
4. При архитектурных проблемах — возвращает Аналитику или создаёт **отдельную архитектурную Issue** (не смешивая с бизнес-Issue).
5. Следит за **единообразием системного промпта и шаблона Issue** у Аналитика и UX-дизайнера.
6. **При конфликте с Тестировщиком приоритет у Тимлида, но он обязан письменно обосновать причину** в комментарии к PR.
