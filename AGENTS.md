# Правила проекта

## Язык

- Все Markdown-документы, Issue, PR, комментарии и отчёты пишите на русском языке.
- Имена файлов, команд, API, библиотек, переменных и функций не переводите.

## Источники истины

- `GitHub Issues` — единственный источник истины для задач: критерии приёмки, обсуждение, статус.
- `GitHub PR` — фактическое состояние кода и доказательства: diff, CI, ревью.
- `AGENTS.md` — правила для людей и агентов.
- `README.md` — описание проекта и процесса.
- `git status`, `git diff`, тесты — фактическое состояние.

`TASKS.md`, `PLAN.md`, `PRODUCT.md` и timestamp-файлы попыток **не используются**. Любой список задач в репозитории запрещён.

## Роли и границы

| Роль | Ответственность | Право решения |
|---|---|---|
| Аналитик | Бизнес-процессы, критерии приёмки, приоритеты | Единственный владелец бизнес-логики |
| UX-дизайнер | Удобство, навигация, доступность | Владелец UX-критериев; по бизнес-логике — только предложение |
| Fullstack | Реализация кода, создание PR | Не принимает решений о слиянии |
| Тестировщик | Соответствие PR критериям, граничные случаи | Владелец качества |
| Тимлид | Архитектура, стек, CI/CD, финальное слияние | Владелец архитектуры; при конфликте с Тестировщиком приоритет у Тимлида с письменным обоснованием |

- UX-дизайнер не создаёт Issue, затрагивающие бизнес-логику — только комментирует Issue Аналитика.
- Fullstack работает с основным агентом, без суб-агентов для написания кода.
- Суб-агент `reviewer` — только чтение, используется Тестировщиком и Тимлидом.

## Git-правила

- Ветки задач создаются от `dev` и сливаются обратно в `dev` через PR.
- Имя ветки: `feat/issue-{номер}-краткое-описание` (тип: `feat`, `fix`, `docs`, `test`, `chore`).
- Сообщение коммита: `тип: описание (#номер)`.
- Заголовок PR: `тип: описание (#номер)` — он же становится сообщением коммита при Squash.
- Слияние только через **Squash and merge**.
- Прямой push в `main` и `dev` запрещён.
- `dev` сливается в `main` только через PR и только когда `dev` стабильна.
- Ветка по умолчанию — `dev`.

## Чтение Issues

Агент читает Issues через `gh` CLI, не через MCP.

```bash
gh issue view <номер> --json title,body,comments --jq '.title + "\n" + .body'
```

- Обязательно используйте `--json`, иначе `gh` может открыть пейджер и заблокировать агента.
- Если вывод длинный, извлекайте нужные поля через `--jq`.
- Агент не создаёт и не закрывает Issues, только читает.

## Формат Issue

Каждая Issue создаётся по шаблону `.github/ISSUE_TEMPLATE/business-task.md`.

Обязательные разделы:
- Пользовательская история
- Затронутые области
- Критерии приёмки в формате «Дано-Когда-Тогда», каждый пункт проверяемый
- Что входит / что не входит
- Способ проверки
- Дополнительный контекст

Issue без критериев приёмки не считается готовой к работе.

## Перед работой

1. Прочитайте Issue, назначенную на вас (статус `ready-for-dev`), включая комментарии.
2. Проверьте `git status`, `git diff` и последние коммиты в ветке `dev`.
3. Создайте ветку от `dev`: `feat/issue-{номер}-краткое-описание`.
4. Если критерии приёмки непонятны — комментарий в Issue, не начинайте код.

## Работа

- Одна небольшая проверяемая задача за итерацию.
- Не переписывайте несвязанные файлы и не добавляйте зависимости без одобрения.
- Реализуйте только критерии приёмки из Issue.
- Перед созданием PR проверьте критерии приёмки локально.
- Для ревью критичных PR используйте модель, отличную от той, что писала код, если это возможно.

## Безопасность

- Не выводите `.env`, токены, ключи, персональные данные и закрытый код.
- Skill может содержать исполняемый код: проверяйте `scripts/`, команды, сеть и разрешения.
- Не выполняйте `sudo`, `curl | bash`, массовое удаление и публикацию данных без подтверждения.
